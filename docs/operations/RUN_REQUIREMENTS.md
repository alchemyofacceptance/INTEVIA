# INTEVIA run requirements (repository copy)

Rendered from practice v1.38 §R, the run operational specification held by the Human Governor's practice. This copy is bound by its byte
digest in the authorised run state file and checked at every launch (R11). On a contradiction between a relay and this copy, the Making
Engine stops and reports the R-number. Do not edit this file except by re-rendering it from §R.

R1. Fail-fast is on for every development, stage-closing, full-verification and delta-verification run; no route disables it.
    Completeness is the required selection executing and passing with fail-fast on.
R2. Clone (template) mode is the development default; fresh mode only where a commission or the Human Governor names it for that run,
    bound by the authority file's digest. A reason alone is refused.
R3. Labels are module.Class or module.Class.method; a module is expanded to its classes and loader-checked before launch.
R4. Resolve the current selection and counts through the loader at launch (unique tests, no duplicates, no failed labels), stored as a
    plan file whose digest is the SHA-256 of its final bytes. Retain the bound preceding run record and parent plan as the rotation and
    coverage basis; compare them with the current resolution and refuse unexplained differences. Earlier counts are never accepted
    without current validation.
R5. After a fail-fast failure, the next attempt is rotated over the same parent plan: invocation A from the unit containing the failing
    test to the end, invocation B (only if A passes) from the start to the unit before it; closure is the union of unique ids on the same
    parent plan and candidate binding, never a sum.
R6. Ordered groups are indivisible and keep their internal order; a failure inside a group starts invocation A at the whole group.
R7. The runner executes exactly the validated plan; executed identifiers equal the plan, or a prefix of it ending at a fail-fast stop.
R8. Every report records the actual mode, fail-fast, plan digest, rotation basis, executed-versus-plan result, and template built or
    reused with real build seconds.
R9. Missing, stale or contradictory inputs refuse before launch with an actionable message naming the R-number; never a silent
    fall-back to another mode.
R10. Full verification runs the complete required suite in its required order; authorised delta verification runs the selection its
    governing decision and impact record require. Both keep fail-fast and their mode requirements; neither is rotated; an unauthorised
    subset is refused.
R11. The repository copy of this specification is bound by content to the authorised run state and checked at launch and
    at handover.
R12. The standard handover carries the specification with its status and the records needed to prepare the next run (state file,
    parent plan, bound preceding run record); the receiving seat's first run relay is built from the handover alone and checked before
    execution.
R13. Every run relay ends with a pre-launch check, one line per applicable requirement.
R14. Before any development launch, the test classes in the changed test files that declare no database are identified mechanically and
    run with fail-fast and database connections forbidden on every alias; the classes, the outcome and the connection-attempt count are
    reported, and "none qualify" is reported explicitly. No database is created.
