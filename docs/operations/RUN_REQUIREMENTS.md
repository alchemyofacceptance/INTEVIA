# INTEVIA run requirements (repository copy) — post-permit v1.1 (16 Oct 2026: R5 rotation code removed; R15 without pyright)

Rendered from practice section R as reset by the Human Governor's decisions TR-1 to TR-4 of 15 October 2026 (the testing reset), reconciled
from the Lead Designer's returns v1.0 section 5.5 and v1.1 and the TU-2a commission. Operative from the first launch after the TU-2a
qualification permit (R5), when the Human Governor has placed this file and a state file binding its digest. This copy is bound by its byte
digest in the authorised run state file and checked at every launch (R11). On a contradiction between a relay and this copy, the Making
Engine stops and reports the R-number. Do not edit this file except by re-rendering it from section R.

R1. Fail-fast is on for every pre-run, development, closure and full run; no route disables it.
    Completeness is the required selection executing and passing with fail-fast on.
R2. Clone (template) mode is the development default; fresh mode only where a commission or the Human Governor names it for that run,
    bound by the authority file's digest. A reason alone is refused. The CI verification route runs in fresh mode by this rule; its per-run
    authority file cites R2, names fresh mode and the step, and is bound by its digest.
R3. Labels are module.Class or module.Class.method, resolved to a plan; a launcher accepts at most twenty labels and otherwise a plan file.
    A module is expanded to its classes and loader-checked before launch.
R4. Resolve the current selection and counts through the loader at launch (unique tests, no duplicates, no failed labels), stored as a
    plan file whose digest is the SHA-256 of its final bytes. Earlier counts are never accepted without current validation.
R5. Rotation is retired, from the first launch after the TU-2a qualification permit, and its code is removed. A run never resumes from a
    failure point and a plan is never required to contain an earlier failed plan. After a failure in a development run, the Making
    Engine diagnoses the failing witness and its directly related cases first, then reruns the complete packet set on the corrected
    candidate before READY. After a failure in a closure run, the cause is diagnosed in development runs and the closure run is rerun whole
    on the resulting candidate. Closure is one complete passing run, never a union.
R6. Ordered groups are indivisible and keep their internal order.
R7. The runner executes exactly the validated plan; executed identifiers equal the plan, or a prefix of it ending at a fail-fast stop.
    The child receives the plan only as a file with its digest; no identifier is placed on a command line.
R8. Every report records the actual mode, fail-fast, plan digest, run kind (pre-run, development, closure, full, qualification),
    executed-versus-plan result, template built or reused with real build seconds, and the per-test timing phases (check, unittest,
    post-teardown, flush) with incomplete phases marked.
R9. Missing, stale or contradictory inputs refuse before launch with an actionable message naming the R-number; never a silent
    fall-back to another mode.
R10. Each commission names its closure: its own Human-launched closure run on the frozen candidate, which is the packet's verification of
    record; or membership of a named shared integration checkpoint with its members and first dependent consumer; or none, only for
    documentation-only work or another case the commission expressly justifies. The full suite runs before merge into main as the Human
    Governor's local run of record, and in CI on pull requests and on main. No closure, checkpoint or full run is rotated; an unauthorised
    subset is refused.
R11. The repository copy of this specification is bound by content to the authorised run state and checked at launch and at handover.
R12. The standard handover carries the specification with its status and the state file; the receiving seat's first run relay is built
    from the handover alone and checked before execution.
R13. Every closure-run and full-run relay ends with a pre-launch check, one line per applicable requirement; development runs record R8's
    fields automatically.
R14. Before any development launch, the test classes in the changed test files that declare no database are identified mechanically and
    run with fail-fast and database connections forbidden on every alias; the classes, the outcome and the connection-attempt count are
    reported, and "none qualify" is reported explicitly. No database is created.
R15. The pre-run, before every development run and after relevant edits: py_compile on every changed file, and R14. A pre-run failure stops
    the launch and is corrected across the whole file before the next pre-run. Pyright is not part of the pre-run (removed by the Human
    Governor's decision of 16 October 2026 after its one trial); any static checker becomes part of it only by a later Human decision.
R16. Named runs. Pre-run: no database; seconds; the Making Engine. Development run: the packet set (the packet's new and changed tests, the
    existing tests the commission names as direct witnesses, and the directly affected guardians and concurrency witnesses); the Making
    Engine under H87 within the commission's budget. Closure run: once, on the frozen candidate, the commission's dependency-argued impact
    set and all 25 guardians; launched by the Human Governor. Full suite: before merge into main, and in CI. The Making Engine proceeds
    without a relay on an in-scope test or product correction, and stops and reports on: budget exhaustion; the same cause recurring after
    a claimed repair, or two correction cycles with no evidenced progress; a required behaviour that is unclear, a test that would need a
    weaker assertion, or allowed paths that must change; an effect outside the authorised work; isolation, protected-database safety,
    evidence identity or reporting integrity not established. A failing test inside scope is not itself a relay.
R17. Isolation. CP-0 before the first test (full capture). Before each test, the light check: protection counts, per-table row counts,
    seed and framework content digests, and the one-statement sequence check, compared with CP-0; on any mismatch, a full capture and
    compare, the checkpoint not established, attribution to the previous test. Full per-test capture for tests marked as running DDL or
    migrations (module, class or method marker), and for any run a commission names with the per-test switch. After any failing or erroring
    test, a full capture once that test's post-teardown has completed. CP-Z after the last test (full capture). The isolation verdict is
    CP-0 met, an established check before every executed test, and CP-Z established when the run completed.
